# Review: retention-bench v0.1

- **Date:** 2026-07-07
- **Scope:** full tree at commit `5183639` — docs, `harness/`, `retention_bench/`, `scorer/`, all seven `suts/`, and the test suite.
- **Method:** static review. The review environment had Python 3.11 while the `cl-benchmark` dependency requires 3.13, so the test suite was not executed.
- **Reviewer:** Claude (AI code review, requested by the maintainer).

---

## Overall verdict

This is an unusually well-thought-out benchmark extension. The core contribution is real and cleanly scoped: CL-Bench has no way to express "the process died and only disk survived," and retention-bench adds exactly that plus a reset-density axis, without forking or re-deriving the upstream metric. The engineering discipline — atomic flush-before-reply, measured rather than nominal `k`, the reconciliation test against CL-Bench's own `mean_gain`, the honest `EXCLUDED` handling of the constructive SUT's collapsed band — is well above what most benchmark repos ship.

The main criticisms are:

1. the hard-reset guarantee is weaker than the docs claim for exactly the SUT class the benchmark targets (multi-process agents);
2. `R(k)` as a *whole-run mean* dilutes the very signal the reset axis exists to measure;
3. a packaging bug breaks non-editable installs;
4. doc/code drift left over from the pivot.

## Concepts

**The metric design is sound, and the validity work is the standout.** `(R − P) / max(C − P, ε)` is a per-SUT band normalisation, and the docs correctly treat its two failure modes: the `C ≈ P` exclusion (with the sharp observation in `docs/metrics.md` that prior saturation makes the benchmark's effective signal model-dependent, so material novelty is a *validity* requirement, not variety) and the warning not to over-interpret narrow bands. The reconciliation argument — that `R(k) − P` must equal CL-Bench's per-instance-matched `mean_gain`, asserted by `tests/test_gain_curve.py:91` against the upstream `build_benchmark_aggregate` rather than a re-implementation — is exactly the right non-tautological check, and it is what makes "we contribute the axis, not a competing formula" credible.

**The reference ladder is excellent benchmark hygiene.** `no_state` / `reset_lossy` / `bounded_memory` / `associative_memory` answer the first reviewer question ("does the metric discriminate?") offline and deterministically. Two touches deserve specific praise: `reset_lossy`'s geometric forgetting gate (`suts/reset_lossy/reset_lossy/clbench_main.py:118`) is the rung that makes the metric read as *graded* rather than binary, and the `bounded_memory` analysis — the FIFO cap lowers the *ceiling*, not retention, so it lands at norm 1.0 — is a genuinely instructive demonstration that the normalisation isolates retention fidelity from capacity. The `no_state` design choice (in-RAM ephemeral rather than truly stateless, so its ceiling is high but everything evaporates at `k ≥ 1`) is the cleanest possible demonstration of what the hard reset erases.

**Conceptual concern 1: `R(k)` is a whole-run mean, which dilutes the reset signal.** A run with one reset at instance 30 of 90 scores 30 instances identically to the ceiling arm before the reset ever happens, so the damage a reset does is averaged against instances it couldn't have affected. Consequences: the curve's sensitivity depends on run length and reset placement, not just on the SUT; and a SUT that *relearns quickly* after a reset is indistinguishable from one that *retained*. For the associative task this mostly washes out (all resets precede the probes), but for BSM-style streams it matters. Consider a complementary post-reset-window reward (mean reward over the first `m` instances after each reset, analogous to the cold-start *compute* metric already specified) — that is the reward-side cold-start curve, and it separates retention from relearning, which is arguably the benchmark's actual question.

**Conceptual concern 2: `k` conflates count with placement.** The measured-`k` decision (`retention_bench/gain_curve.py:19`) is right, but two arms with the same `k` and different placements are different experiments — the docs know this (that is the whole `--reset-at` drift story) yet the headline curve indexes points by `k` alone. Also worth a footnote: in a `reset_lossy`-style mechanism, the *per-probe* effective reset count varies across the run (a probe at ordinal 11 under `every_1` has survived 10 resets; one at ordinal 26 has survived 25), so the point labelled `k=25` is really an aggregate over heterogeneous per-fact exposures. Fine for a deterministic reference; a real SUT's curve inherits the same ambiguity.

**Conceptual concern 3: no variance story yet.** Every arm is a single run. `docs/metrics.md` §Reporting requires error bars and seed counts, but nothing in `gain_curve.py` computes them, and for a stochastic SUT (`notes_llm`) a one-run point on a normalised axis with a possibly-narrow band can be dominated by noise. With binary rewards over 26 instances, the reward resolution is ~0.038 — comparable to `ε = 0.05` itself. A bootstrap over per-instance outcomes (every point already keeps `outcomes` precisely "for post-hoc reanalysis") would be cheap and would make the curve publishable. Related: `ε` is an absolute 0.05, but on tasks whose whole-run mean is structurally compressed by unscored train instances (`r_max = 16/26 ≈ 0.615`), 0.05 of nominal range is ~8% of achievable range; `ε` should probably scale with `r_max`.

**The honest negative result is a strength, not a weakness.** Shipping a constructive SUT whose band correctly renders `EXCLUDED`, and saying so in the README, docs, and the SUT's own docstring, is the right call, and the development brief's milestone framing ("milestone 2 — a non-degenerate band — is the gap") sets up the follow-on work honestly.

## Architecture

The layering is clean and the boundaries are in the right places:

- **The mechanism-agnostic SUT contract is the strongest design decision.** One JSONL process protocol with a per-query `response_schema`, under which fine-tuning, notes, RAG, and structural growth are indistinguishable to the harness — that is what makes the "constructive systems are first-class" claim true rather than aspirational, and `ContainerLaunch` reusing the identical wire contract confirms the seam is real.
- **`retention_bench/_clbench.py` as the single import chokepoint** for CL-Bench's unfortunate `src` package name is exactly how to consume a dependency with a packaging smell — one file changes if upstream ever renames.
- **`scorer/aggregate.py` as the single home of the band formula** (all 5 lines of it) is a bit of ceremony for one function, but the "one definition, every consumer" rationale is legitimate.
- **System-side reset scheduling** (run the runner with `reset_between_instances=False`, decide inside `observe()`) is the right inversion — it gets arbitrary densities without touching upstream, and `EveryNInstances(1)`+wipe reproducing CL-Bench's stateless baseline in the same accounting path is elegant.

Two architectural gripes:

1. **Book-track residue.** `harness/sut_process.py`'s module docstring (lines 3–16) still documents the retired READ/QUIZ framing; `send_event` (line 223) is dead on the live path; the manifest carries a legacy `entrypoint` field. More broadly, the internal pivot codenames — C0, C2, C9, C10, C20, B4a, B13, RB-2b/c — pervade docstrings and docs. An external reader can follow the code *despite* them, not because of them; they reference `.tasks/` debriefs and archive docs that are not on this branch. For a public v0.1 they should be swept into plain-language comments.
2. **Reference SUT duplication.** Four of the ladder SUTs share ~80% of their code (the regexes, `_match`, `_load_state`/`_save_state`, `_iter_requests`). Self-contained packages are defensible (each SUT is meant to be independently launchable), but a tiny shared `sut_kit` would cut the surface for bugs like a regex drifting in one copy. At four copies it is borderline; at six it won't be.

## Implementation — findings by severity

**1. The "hard RESET" doesn't kill process trees.** `kill_sut` (`harness/sut_process.py:313`) SIGKILLs only the direct child; there is no `start_new_session=True` at spawn and no `killpg`. `docs/sut-interface.md` says children "MUST be killable by SIGKILL to the parent's process group" — but the harness never creates or signals a process group, so that sentence describes enforcement that does not exist. This matters because agent scaffolds — a target SUT class — routinely spawn children, and a surviving child is a hole in the benchmark's core semantics: it can keep in-memory state alive across the "discontinuity" (e.g., a helper server the respawned SUT reconnects to via a socket in the survive-dir). Today the contract is trust-based; `setsid` + `killpg` is a ~5-line change that makes it mechanical for subprocess mode. (Container mode already enforces this properly via `docker rm -f` — worth stating in the docs that containers are the *enforced* path.)

**2. Timeout doesn't do what the docs say.** `docs/sut-interface.md:147` says "On timeout the harness SIGKILLs the SUT process and raises `SUTTimeout`", but `SubprocessSystem._exchange` (`retention_bench/system.py:352`) only raises; the wedged process lives on until `shutdown()` or the GC finalizer. Either kill on timeout or fix the doc.

**3. `_readline_with_timeout` has two buffering edges** (`harness/sut_process.py:280`): it `select()`s on the raw fd, then calls buffered-text `readline()`. (a) A reply written in chunks without a trailing newline makes `readline()` block *past* the timeout indefinitely. (b) If a misbehaving SUT ever emits two lines at once, the first `readline()` pulls both into the TextIO buffer, and the next `select()` can time out with a complete reply already sitting in Python's buffer — a spurious `SUTTimeout` that would be miserable to debug. Strict one-in-one-out keeps the happy path safe, but the failure modes of the enforcement mechanism land exactly on misbehaving SUTs, where clear errors matter most. A non-blocking fd with an explicit line buffer (or a reader thread) fixes both.

**4. Packaging bug: `scorer` isn't packaged but shipped code imports it.** `pyproject.toml:43` includes only `harness*` and `retention_bench*`, yet `retention_bench/gain_curve.py:55` does `from scorer.aggregate import …`, and the `retention-bench` console script points at that module. A non-editable `pip install .` produces a broken install; `pip install -e .` works only because the editable path leaks the repo root. Either add `scorer*` to the include list or (preferably) fold the 5-line module into `retention_bench` and keep `scorer` as a shim.

**5. `run_reset_sweep` never shuts its systems down** (`retention_bench/gain_curve.py:175`–181). The class ships a context manager and a docstring that warns "call `shutdown()` … to avoid leaking the final container," but the sweep itself relies on CPython refcounting to trigger the weakref finalizer. Works today in CPython/subprocess mode; leaks the final container per arm under any GC delay or exception. `with make_system(...) as system:` is right there.

**6. `r_max` is stale for non-default task configs.** `SymbolicAssociativeRetentionTask.r_max = 16/26` is a class attribute computed for the default schedule (`retention_bench/tasks/symbolic_associative_retention.py:51`); with `num_exposures=2` the true max mean is 16/36. retention-bench itself never uses `r_max` (it measures `C`), so the blast radius is CL-Bench-side aggregates only — but it should be computed per-instance-schedule in `build_canonical_run_state`.

Smaller items:

- `_split_reply` (`retention_bench/system.py:422`): `reply.get("resource") or {}` silently converts falsy non-dict `resource` values (`0`, `""`, `false`) into `{}` instead of raising the declared `SUTError`; and a schema-nonconforming `action` surfaces as a raw pydantic `ValidationError` rather than a `SUTError`, so the error taxonomy is inconsistent at exactly the contract boundary.
- The `gain_curve` CLI doesn't expose `--stderr-log`, and `spawn_sut` defaults SUT stderr to `DEVNULL` — so a crashing SUT in a sweep yields only "SUT closed stdout before replying (exit=1)" with its diagnostics discarded. Default stderr into the per-arm state dir; it is the first thing a SUT author will need.
- Env-var knobs (`RESET_LOSSY_RATE`, `BOUNDED_MEMORY_CAP`) silently fall back to defaults on invalid values. For a *benchmark*, a typo'd experiment parameter silently running the default is worse than a crash — raise instead.
- `checkpoint.load` uses `torch.load(weights_only=False)` with a fair rationale (own survive-dir), but if survive-dirs ever become shared/auditable artifacts (the docs mention post-hoc auditor diffs), that is an arbitrary-code-execution vector to revisit.
- `SubprocessSystem.__init__` doesn't create the `.harness/` reserved dir that `dir_lifecycle.create_dir` does — harmless, but the two dir-creation paths have drifted.

## Tests

Strong for a v0.1: end-to-end through CL-Bench's real runner (not a mock), the load-bearing reconciliation assertion, wipe-vs-persist semantics, measured-`k` and explicit-boundary behaviour, container-name uniqueness, a fake-OpenAI shim so `notes_llm` is testable offline, and docker-gated container tests kept separate. The counter SUT is a well-chosen minimal fixture.

Gaps: nothing exercises the `SUTTimeout` path or a mid-run SUT crash (the failure modes in finding 3 are untested), nothing tests a SUT that spawns a child (finding 1), and — notably — **there is no CI config in the repo at all**. Given the suite skips cleanly without `cl-benchmark`, a plain GitHub Actions job on 3.13 would be cheap and would also catch the packaging bug via a non-editable install step.

## Docs

The documentation is a genuine strength — `sut-interface.md` is a real spec (MUST/MUST NOT, worked example, manifest table), and `metrics.md`'s validity sections read like someone who has reviewed benchmarks before. Three issues:

1. **Aspiration vs. implementation isn't marked** — AURC, half-retention `k`, cold-start cost, wall-clock, and the shape classifier are all presented in `metrics.md` as if reported, but none are computed anywhere; a "status: specified / implemented" marker per metric would prevent over-claiming.
2. **Dangling references** — `docs/clbench-pivot-plan.md`, `docs/clbench-task-triage.md`, `docs/trace-schema.md`, `docs/task-definition-schema.md`, and `.tasks/` are cited from shipped docstrings and the development brief but do not exist on this branch.
3. **Developer-machine residue** — the `_clbench.py` import-error message tells users to run `/home/agent/src/cl-bench/.venv/bin/python` (`retention_bench/_clbench.py:50`), a path from the original dev container, not theirs.

## Suggested priority order

1. Process-group kill (+ kill-on-timeout, + doc alignment) — this is the integrity of the headline mechanism.
2. Package `scorer` (or inline it) and add CI with a non-editable install check.
3. Use the context manager in `run_reset_sweep`; expose `--stderr-log` (default it on).
4. Bootstrap CIs over per-instance outcomes; consider a post-reset-window reward alongside the whole-run `R(k)`.
5. A doc pass: strip pivot codenames, mark unimplemented metrics, fix dangling references.

None of this undercuts the core: the reset semantics are real (state provably crosses a SIGKILL only via disk), the metric reconciles with upstream by construction and by test, and the reference ladder demonstrates discrimination honestly. With the process-tree fix and a variance story, the measurement core is trustworthy for external SUT authors.
